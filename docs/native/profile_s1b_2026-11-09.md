# Console CPU profile — P2a-2 in S1b (2026-11-09)

Run `prof1_p2a`: out/builds/p2a2_2201 (P2a-2) + tools/console/ab_p1_profile.toml (`banjo_cpu_profiler = true`: every
thread sampled every 2 ms, a block every 30 s), New Bodhum field from Save Data 01, 150 s no input, handheld clocks.
Analysed: the last 30 s block (field only), offsets named with tools/console/prof_agg.py + elf_sym.py (own ELF64
symbol reader; the old symbolizer wants devkitA64 nm, this project builds with LLVM:
tools/console/switch_cpu_profile_ffns.py falls back to _tools/llvm/bin/llvm-nm.exe). Full table:
out/profiles/prof1_p2a_agg_last.txt. Raw log: logs/switch/unknown/prof1_p2a/logs/rex/banjo_profiler.log.

Note on reading it: a sample whose PC is right after an `svc` (svcArbitrateUnlock+4, svcSleepThread, svcResetSignal)
is a thread blocked in the kernel, not CPU time. The profiler counts it under "running".

## Main thread (the frame's critical path; ~62 ms a frame in S1b)
| share | what |
|---|---|
| **68.1 %** | guest code: **flat** — top 10 functions 7.6 %, top 50 20.3 %, top 200 36.8 %, top 1,000 60.3 %; 2,010 functions sampled |
| 18.6 % | blocked in system calls (see below) |
| 5.4 % | renderer work on the game thread (D3D hooks: CaptureDelta 2.0 %, SetStreamSource, Ffxiii2StableSurface …) |
| 3.7 % | libc/libnx (memcpy, mutexLock/Unlock) |
| 3.1 % | rex runtime/kernel (RtlEnterCriticalSection_raw, ObjectTable::LookupObject …) |

Guest code by form: fast bodies 39.5 %, DEFINE bodies 28.7 % (`sub_X` 19.6 %, `__imp__sub_X` 9.1 %) of all
main-thread samples — **42 % of the guest time is in functions without a fast entry** (only indirect callers, e.g.
virtual methods, or in the 764-name exclude list). Top guest functions: __fast_sub_8228EFC0 1.56 %, sub_8297C850
1.02 % (DEFINE, indirect-only), __fast_sub_82886250 0.79 %, __imp__sub_8297B3E0 0.78 %, __imp__sub_829A4890 0.70 %.

Where the main thread blocks (2,573 of 13,809 samples, from the stacks of the system calls):
- ~56 %: NtWaitForSingleObjectEx → XObject::Wait → PosixConditionBase::Wait (condvar): the game waits for an event
  (WaitForSingleObjectEx wrapper sub_82B69618) — most likely its worker threads or the frame pacing.
- ~12 %: KeDelayExecutionThread → XThread::Delay → MaybeYield → sched_yield/svcSleepThread from the Sleep wrapper
  sub_82B69868 called by sub_82886578: a guest sleep/poll loop.
- ~11 %: RtlEnterCriticalSection_raw → xeKeWaitForSingleObject: critical-section contention with another thread.
- the rest: pthread/rmutex locks in ObjectTable::LookupObject and the condvar, notify_one of the render thread queue.

## Other threads (last block)
- Render thread ("thread"): ~20 % busy (DrawStateLocked, PagesClean, BindStreams, uploads), the rest waiting.
- XThread58008460: ~50 % busy: sub_82A34BB0 15.4 %, __fast_sub_82BB4008 7.9 %, sub_82B99580 4.3 %,
  __fast_sub_82BACAC0 3.3 % (not identified yet).
- XThread69734040: 95 % in svcSleepThread (a sleeping poll thread, cheap). XMA decoder ~20 % busy, audio worker idle.
- XThread56CB4A20 (and two siblings): ~40 % busy, the same game functions as the main thread (job workers).

## What this means for the next steps
1. The guest code is flat: no single hot function to hand-optimise. Broad codegen work stays the lever.
2. 42 % of the main thread's guest time runs in DEFINE (old-ABI) bodies. Next study: why each of the top DEFINE
   functions has no fast entry (indirect-only vs exclude list), and whether a fast entry plus a ctx-ABI wrapper for the
   indirect table would help them (their own calls already go fast; the gain would be in their argument/return
   traffic) — measure on a sample of functions before changing the generator.
3. ~19 % blocked: find what the main thread waits for (deeper stacks: the profiler keeps 8 frames; a guest-level
   trace of sub_82B69618's callers and wait times would name the event). If it is its own workers, speeding them
   (job threads ~40 % busy each) or the critical sections they share is the lever, not the main thread.
4. Renderer hooks on the game thread 5.4 %: CaptureDelta is the largest; it is exact work (pixel-identical), only
   cheaper forms count.

## P3 candidates from the profile + a census of the remaining ctx traffic (P2a-2 tree, 2026-11-09)
Static ctx references left in tree/app/generated (all files): r3-r10 558,623; **v0-v13 105,316**; lr 99,991; f1-f13 56,767;
**v32-v127 55,951**; f0 18,308; r0/r2/r11-r13 17,831; r1 10,885 (the rest r1l); ctr 4,242; v14-v31 732; f14-f31 342.
- **Vector registers are not in any localisation**: args_in_registers handles r3-r10/f1-f13 (+ a few scratch and lr),
  non_argument_as_local the scalar non-arguments. Example: the main thread's top function __fast_sub_8228EFC0 (1.56 %,
  a 4x4 matrix product) keeps v0-v13 in ctx: every vspltw/vmaddfp result is a 16-byte store to ctx and a reload.
  Candidate P3a: extend the generator's dataflow (sdk/src/codegen/args_in_registers.cpp, Par/Fw/Ex sets) to the
  VMX registers (vector args v2-v13 by value or as locals; locals for the rest; exports only where a caller reads).
  Before the generator change: estimate with a sample (count ctx.vN stores in the top 200 profiled functions).
- Exports at exits: e.g. __fast_sub_8228EFC0 ends with ctx.r9 = r9; ctx.r10 = r10 (its Ex set): check why (a caller
  reading r9/r10 after the call, or a conservative indirect-caller assumption).
- 17,195 functions keep one body (indirect callers only); 42 % of the main thread's guest time runs in such DEFINE
  bodies: their argument loads/exports are the old ABI; part of the r3-r10 count above.
- Estimate on the main thread's top 200 profiled functions (5,083 samples, ~37 % of the main thread; 197 bodies,
  67,255 statements): 20,857 ctx register references, **8,040 of them vector (2,428 vector stores to ctx)**; 71 of the
  197 functions use ctx.vN and hold 2,201 of the samples (~16 % of the main thread). If the vector ctx traffic is 15-25 %
  of those functions' time, P3a is worth ~2.5-4 % of the main thread: measurable only with ≥ 4 pairs (see P2b).
  The other 12.8 k scalar ctx references in these functions (exports, old-ABI calls, DEFINE bodies) are the second
  half of the same question.

## Disassembly check of the hot functions (2026-11-09 05:00 UTC; out/profiles/dis_*.txt, llvm-objdump of the P2a-2 ELF)
- __fast_sub_8228EFC0 (the matrix product): the compiler already keeps v0-v13 in registers and stores only the final
  value of each to ctx (14 q-register stores at the end, no reloads): `ctx` is __restrict, so the intermediate ctx
  traffic in the C++ text is not in the machine code. **P3a (vector registers as locals) would only remove those exit
  stores: estimated ~1 % of the main thread → deprioritised.**
- The big DEFINE bodies are dominated by **host stack spills** (register pressure): sub_8297C850 (4,393 instructions,
  1.0 % of the main thread) has 1,615 memory operations, 783 of them on the host stack (408 x/w spill stores+loads,
  40 q); __imp__sub_8297B3E0 388 of 1,305. Guest memory (base + uxtw index) and ctx are the smaller part.
  Locals are zero-initialised (`PPCRegister r11{}`): spilled ones cost a store at entry (`str xzr, [sp, …]`).
- Compiler: devkitA64 GCC -O3 -march=armv8-a+crc+crypto -mtune=cortex-a57, -mearly-ra=none (early RA miscompiles,
  CMake comment), -fno-strict-aliasing, -ffp-contract=off. Every exact BANJO_GEN_* option is already ON; the OFF ones
  are not exact (frame elisions, -fno-trapping-math) or test aids.

## Where 30 fps is in S1b
- GPU alone 34 ms a frame at native 720p: above the 33.33 ms budget even with an infinitely fast CPU. The renderer's
  dynamic resolution exists as an option (banjo_renut_dynamic_resolution, default off in this project).
- Main thread 62 ms: guest code ~42 ms (flat), waiting ~12 ms (mostly for the game's own job workers), renderer hooks
  ~3 ms, runtime/libc ~4 ms.
- Remaining CPU levers, none of them a quick exact pass any more: (1) register pressure in huge functions (generator:
  narrower live ranges, no zero-init of locals that are written before read); (2) the job-worker critical path (the
  main thread waits ~12 ms/frame for its workers); (3) threads/priorities (needs the user's approval: threading
  change); (4) renderer work on the game thread (CaptureDelta).
